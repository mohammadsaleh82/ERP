# پشته فناوری و استانداردهای فنی (Technology Stack)

این سند مشخصات دقیق پشته فناوری، نسخه‌ها، دلایل انتخاب و گزینه‌های جایگزین رد شده را برای بخش‌های مختلف سیستم ERP تعیین می‌کند.

## ۲. دلایل فنی انتخاب و مقایسه با گزینه‌های رد شده

### ۲.۱. چرا Mapster به جای AutoMapper؟
- **کارایی و سرعت پردازش:** در سیستم‌های ERP که شامل گزارش‌های مالی بزرگ با ده‌ها هزار ردیف هستند، AutoMapper به دلیل استفاده سنگین از Reflection بار محاسباتی و زمان GC بالایی تحمیل می‌کند. Mapster از طریق Expression Trees کدی معادل مپینگ دستی تولید کرده و به مراتب سریع‌تر و سبک‌تر عمل می‌کند.
- **شفافیت تنظیمات:** تعریف نگاشت‌ها در Mapster بدون پیچیدگی و خطاهای زمان اجرا در AutoMapper است.

### ۲.۲. چرا PostgreSQL به جای Microsoft SQL Server یا Oracle؟
- **هزینه لایسنسینگ:** برای یک سرویس SaaS ابری چندمشتریه، هزینه‌های سرسام‌آور لایسنس Per-Core برای SQL Server یا Oracle مانع جدی رشد اقتصادی است.
- **قابلیت‌های بومی ویژه:** PostgreSQL پشتیبانی تراز اول از **Row-Level Security (RLS)** ارائه می‌دهد که ستون فقرات امنیت Multi-Tenancy ما در سطح پایگاه داده است. همچنین قابلیت‌های پیشرفته JSONB برای ذخیره تاریخچه تغییرات (Audit Trails) و ایندکس‌های BRIN/GIN برای لاگ‌های حجیم بی‌رقیب است.

### ۲.۳. چرا React + Vite + shadcn/ui به جای کامپوننت‌های سنگین آماده (MUI / Ant Design)؟
- **حق مالکیت کد (Code Ownership):** در shadcn/ui کد کامپوننت‌ها به عنوان بخشی از پروژه شما تزریق می‌شود (Copy-Paste Component Model)، بنابراین تیم توسعه کنترل ۱۰۰٪ بر روی رفتار، استایل، قابلیت دسترسی (Accessibility) و تغییرات دارد و وابسته به تصمیمات پکیج‌های خارجی نمی‌ماند.
- **سازگاری کامل با RTL و فونت‌های فارسی:** پیاده‌سازی زبان فارسی، راست‌به‌چپ (RTL) و فونت‌های استاندارد سازمانی (مانند Vazirmatn یا IRANSans) در Tailwind CSS بسیار طبیعی‌تر و بدون دردسر Overwrite کردن فایل‌های استایل سنگین انجام می‌شود.

### ۲.۴. معماری ماژولار در مقابل مایکروسرویس
- **سادگی دپلویمنت:** تمام سیستم به صورت یک سرویس مجتمع در قالب کانتینر داکر ران می‌شود.
- **تضمین تراکنش‌های مالی:** صدور سند مالی نیازمند تایید انبار، خزانه‌داری یا فروش است. انجام این فرآیند در مایکروسرویس مستلزم الگوهای Saga و Eventual Consistency است که در صورت بروز قطعی شبکه می‌تواند منجر به اسناد بدون تراز و خطاهای حسابرسی شود.

## ۳. استاندارد زمان و تاریخ

### ۳.۱. سمت Backend و دیتابیس
- تمام فیلدهای تاریخی و زمانی در پایگاه داده باید با نوع `timestamp with time zone` (در EF Core معادل `DateTimeOffset` یا `DateTime` با `DateTimeKind.Utc`) ذخیره شوند.
- هیچ تاریخ شمسی به صورت رشته‌ای یا عددی ذخیره نمی‌شود مگر فیلدهای محاسباتی یا فیلترهای سال/دوره مالی (مانند `FiscalYearId = 1403`).
- ذخیره‌سازی همواره بر پایه ساعت گرینویچ (UTC) است.

### ۳.۲. سمت Frontend
- ورودی و خروجی کامپوننت‌های کاربری (Date Picker و تقویم‌ها) با تقویم استاندارد هجری شمسی (Jalali) کار می‌کنند.
- کتابخانه‌های مجاز در فرانت‌اند: `date-fns-jalali` جهت محاسبات تقویم و تبدیل تاریخ.
- در زمان ارسال داده به API، تاریخ به استاندارد ISO 8601 UTC تبدیل و ارسال می‌شود.

## ۴. استانداردهای پکیج‌ها و مدیریت وابستگی‌ها

1. تمام پکیج‌های پروژه بک‌اند باید با استفاده از ویژگی **Directory.Packages.props** مدیریت شوند (Central Package Management - CPM) تا از ناهماهنگی نسخه پکیج‌ها در ماژول‌های مختلف جلوگیری شود.
2. هیچ ماژولی مجاز نیست بدون تایید تیم معماری، پکیج شخص ثالث جدید به پروژه اضافه کند.
3. در فرانت‌اند از پکیج‌منیجر `pnpm` یا `npm` به همراه Lockfile معتبر جهت تضمین یکسانی ساخت در محیط‌های مختلف استفاده می‌شود.
